# Анализ Reality-адресов для Hasta-Vaquet

> **Дата:** 2026-05-30  
> **Сервер:** 45.134.39.18:443 (Xray Reality)  
> **Текущий dest:** `www.microsoft.com:443`

---

## 1. Введение

Протокол Xray Reality маскирует TLS-трафик под реальное HTTPS-соединение. Параметр `dest` определяет, сертификат какого сайта будет использовать сервер для TLS-рукопожатия. От правильного выбора `dest` напрямую зависит устойчивость к DPI (Deep Packet Inspection).

Ключевые критерии:

1. **Достоверность отпечатка TLS** — сервер должен использовать TLS 1.3 со стандартными шифронаборами.
2. **Глобальная доступность** — сайт должен быть разрешён во всех юрисдикциях (не заблокирован цензурой).
3. **Правдоподобие трафика** — DPI не должен подозревать, что клиент имитирует соединение.
4. **Низкая задержка** — сервер `dest` должен быть отзывчивым и географически распределённым.

### 2.1 `www.microsoft.com` — ТЕКУЩИЙ ДЕФОЛТ

| Критерий | Оценка |
|---|---|
| **TLS-отпечаток** | TLS 1.3, шифронаборы: `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`. Сервер Microsoft использует стандартный отпечаток, хорошо маскируется под Reality. |
| **Риск блокировки** | **Низкий.** Microsoft — глобальный вендор ОС, облачных сервисов (Azure, Office 365). Блокировка приведёт к коллапсу корпоративных коммуникаций. |
| **Правдоподобие** | Высокое. Миллиарды устройств ежедневно стучатся к Microsoft (телеметрия Windows, обновления, Office). |
| **Задержка** | Низкая. Azure CDN с нодами по всему миру (Anycast). |
| **Вердикт** | ✅ **Отличный выбор. De facto стандарт для Reality.** |

**Дополнительно:** Microsoft активно использует собственные протоколы (QUIC, MS-SQH), что создаёт дополнительный «шум» для DPI-анализатора.

### 2.3 `www.cloudflare.com`

**Предостережение:** В некоторых странах (Китай) Cloudflare подвергается периодической деградации трафика. Для РФ — стабилен.

## 4. Рекомендация: стратегия ротации `dest` и `serverNames`

### 4.1 Основной dest (primary)

**Рекомендуется:** `www.microsoft.com:443` — оставить как основной.

Причины:
- Уже работает и проверен
- Минимальный риск блокировки
- Отличное правдоподобие трафика

### 4.2 Резервные dest (ротация)

Регулярная ротация `dest` и `serverNames` затрудняет DPI-профилирование. Рекомендуемый набор:

```
serverNames: [
  "www.microsoft.com",
  "microsoft.com",
  "www.bing.com",
  "cdn.jsdelivr.net",
  "www.apple.com",
  "www.amazon.com",
  "www.cloudflare.com",
  "www.wikipedia.org"
]
```

### 4.3 Стратегия ротации

**Вариант A — Ротация на сервере (ручная):**
Менять `dest` в `xray_config.json` раз в 1-4 недели. Клиенты обновляют `serverName` и `publicKey` (если ключи перегенерированы).

**Вариант B — Множественные inbound (продвинутый):**
Создать несколько inbound-секций в Xray на одном порту с разными `dest`. DPI сложнее профилировать недетерминированный выбор destination.

```json
{
  "inbounds": [
    {
      "port": 443,
      "protocol": "vless",
      "tag": "reality-ms",
      "settings": { ... },
      "streamSettings": {
        "security": "reality",
        "realitySettings": {
          "dest": "www.microsoft.com:443",
          "serverNames": ["www.microsoft.com", "microsoft.com"],
          "privateKey": "...",
          "shortIds": ["19e72187"]
        }
      }
    },
    {
      "port": 443,
      "protocol": "vless",
      "tag": "reality-cdn",
      "settings": { ... },
      "streamSettings": {
        "security": "reality",
        "realitySettings": {
          "dest": "cdn.jsdelivr.net:443",
          "serverNames": ["cdn.jsdelivr.net"],
          "privateKey": "...",
          "shortIds": ["a3f8c2b1"]
        }
      }
    }
  ]
}
```

> **Примечание:** Xray поддерживает несколько inbound на одном порту (через разные `tag`). Reality выбирает destination по `serverNames` и `shortIds` клиента. Клиенты могут быть распределены по разным `shortIds` для разных `dest`.

## 5. Рекомендуемая конфигурация сервера

```json
{
  "dest": "www.microsoft.com:443",
  "serverNames": [
    "www.microsoft.com",
    "microsoft.com",
    "www.bing.com",
    "www.apple.com",
    "cdn.jsdelivr.net",
    "www.cloudflare.com",
    "www.amazon.com",
    "www.wikipedia.org"
  ],
  "shortIds": ["19e72187", "a3f8c2b1", "b4d9e3f0"],
  "privateKey": "eJvaNmNJP-X6l2MprNA8KWPGV0aRgG_er6jArLrKZmY",
  "maxTimeDiff": 30000
}
```

- `serverNames` — расширенный список для маскировки и гибкости
- `shortIds` — зарезервировано для будущей мульти-клиентской маршрутизации
- `maxTimeDiff` — 30 секунд достаточно; слишком большое значение снижает безопасность

### 5.1 Клиентская конфигурация (рекомендуемая)

```json
{
  "outbounds": [{
    "protocol": "vless",
    "settings": {
      "vnext": [{
        "address": "45.134.39.18",
        "port": 443,
        "users": [{
          "id": "a72cda52-caa6-4642-a32c-8b40e9c98632",
          "encryption": "none",
          "flow": "xtls-rprx-vision"
        }]
      }]
    },
    "streamSettings": {
      "network": "tcp",
      "security": "reality",
      "realitySettings": {
        "fingerprint": "chrome",
        "serverName": "www.microsoft.com",
        "publicKey": "GVD5f2lVPEiIKGxn0ZjWIaNu43OUuQIzpmGMw7XYbQs",
        "shortId": "19e72187"
      }
    }
  }]
}
```

**Параметр `fingerprint`:** Всегда использовать `"chrome"`. Chrome — самый популярный браузер (~65% рынка), его отпечаток TLS — наиболее естественный и наименее подозрительный для DPI.

## 6. Интеграция Reality в Hasta-Vaquet Go-клиент

### 6.1 Текущая архитектура клиента

Клиент Hasta-Vaquet использует:
- **Транспорты:** Raw UDP, WSS (gorilla/websocket), QUIC-header UDP
- **Шифрование:** собственное (`CipherPack` с AES-256-GCM + ChaCha20)
- **TLS:** uTLS с Chrome-отпечатком (для WSS)
- **TUN:** Wintun (Windows), системный TUN (Linux/Android)

Reality требует другого подхода: вместо WSS-over-CDN — прямое TCP-соединение с Reality-сервером, VLESS-заголовок и XTLS-Vision flow.

### 6.2 Варианты реализации

---

#### Вариант A: Xray-core как библиотека

**Описание:** Импортировать `github.com/xtls/xray-core` и вызывать его OutboundHandler.

```go
import (
    "github.com/xtls/xray-core/app/proxyman/outbound"
    "github.com/xtls/xray-core/proxy/vless/outbound"
    "github.com/xtls/xray-core/transport/internet"
)
```

**Плюсы:**
- Полная поддержка Reality, VLESS, XTLS-Vision «из коробки»
- Минимум кода для интеграции
- Сообщество поддерживает совместимость

**Минусы:**
- **Огромный dependency weight** — Xray-core тянет `google.golang.org/grpc`, `google.golang.org/protobuf`, `lucas-clemente/quic-go`, десятки других зависимостей
- Сложная сборка с build tags (CGO может потребоваться)
- Размер бинарника увеличится на 15-25 МБ
- Конфликты с текущими зависимостями (например, разные версии uTLS)

| Аспект | Оценка |
|---|---|
| **Implementation effort** | Низкий (использовать готовый outbound) |
| **Dependency weight** | 🔴 **Heavy** (десятки новых зависимостей) |
| **Performance impact** | 🟢 None (на уровне Go-early костылей) |
| **Long-term maintainability** | 🟡 Okay (но обновления Xray-core могут ломать API) |

**Вердикт:** Подходит для быстрого прототипа, но не для production-бинарника.

#### Вариант B: uTLS + ручная реализация Reality handshake

**Описание:** Реализовать Reality handshake самостоятельно, используя уже имеющийся uTLS (версия 1.6.7).

Reality handshake:

1. **TCP-соединение** с сервером (`45.134.39.18:443`)
2. **TLS ClientHello** с uTLS (Chrome-отпечаток, с SNI = `serverName`)
3. **Получение ServerHello** от сервера Reality, который использует сертификат `dest`
4. **Отправка VLESS-заголовка** (зашифрованный x25519-ключ, UUID пользователя, shortId)
5. **XTLS-Vision flow** — прямая пересылка трафика через VLESS-туннель

```go
type RealityConn struct {
    tcpConn net.Conn
    utls    *utls.UConn
    session *vless.Session
}

func DialReality(ctx context.Context, server string, port int, 
    serverName string, shortID uint16, userID string,
    publicKey string) (*RealityConn, error) {
    
    // 1. TCP dial
    tcpConn, err := net.DialTimeout("tcp", 
        net.JoinHostPort(server, strconv.Itoa(port)), 10*time.Second)
    
    // 2. uTLS with Reality-specific extensions
    uconn := utls.UClient(tcpConn, &utls.Config{
        ServerName: serverName,
    }, utls.HelloChrome_Auto)
    
    // 3. x25519 key exchange + Reality padding
    // ... (см. ниже)
    
    // 4. VLESS header
    // ... (VLESS-заголовок: auth, command, port, address)
    
    // 5. Vision flow start
    // ...
}
```

**Необходимые компоненты:**
- **x25519 key exchange** — `golang.org/x/crypto/curve25519` (уже в `go.sum` как transitive dep)
- **VLESS protocol encoding** — байтовый протокол (не Protobuf). VLESS-заголовок ≈ 1-256 байт
- **uTLS custom extensions** — Reality требует специфичных TLS-расширений (PaddingExt, пакет с маской)
- **Vision flow** — MUX для разбивки трафика на «реалистичные» сегменты

| Аспект | Оценка |
|---|---|
| **Implementation effort** | 🔴 **Высокий** (протокол недокументирован; реверс-инжиниринг Xray-core) |
| **Dependency weight** | 🟢 **Light** (уже есть uTLS + x/crypto) |
| **Performance impact** | 🟢 None |
| **Long-term maintainability** | 🔴 **Poor** (нужно следить за изменениями протокола; баги в ручной реализации) |

**Вердикт:** Технически возможно, но крайне трудоёмко. Реализация Reality-расширений (AuthID, Padding) требует полного понимания протокола.

#### Вариант C: Sing-box Reality (рекомендуемый)

**Описание:** Использовать `github.com/sagernet/sing-box` как библиотеку или скопировать его V2Ray Reality-реализацию.

Sing-box имеет более чистую архитектуру, чем Xray-core:

- Меньше transitive dependencies
- Модульная структура (можно взять только `transport/internet/reality`)
- Написана с учётом uTLS (уже используется в Hasta-Vaquet)
- Активно поддерживается (SagerNet)

```go
import (
    "github.com/sagernet/sing-box/transport/internet/reality"
    "github.com/sagernet/sing-box/transport/vless"
)
```

**Плюсы:**
- Легче Xray-core (~в 5 раз меньше зависимостей)
- Reality-реализация отвязана от Protobuf
- Уже использует uTLS, как и Hasta-Vaquet
- Понимание кода выше (Go-idioms, без Proto-магии)

**Минусы:**
- Sing-box меняет API нестабильно (релизы rarely, but breaking)
- Может потребоваться копирование vendor-кода (`sing-box/transport/internet/reality`)
- Часть кода (VLESS) переплетена с sing-box DI

| Аспект | Оценка |
|---|---|
| **Implementation effort** | 🟡 Средний (адаптировать вендор-копию) |
| **Dependency weight** | 🟡 Medium (sing-box легче Xray-core, но всё же весом) |
| **Performance impact** | 🟢 None |
| **Long-term maintainability** | 🟡 Okay (breaking changes могут потребовать адаптации) |

#### Вариант D: Легковесная Reality-библиотека (идеальный, но гипотетический)

**Описание:** Создать минимальную библиотеку для Reality handshake, отделив её от Xray-core/sing-box.

**Состав библиотеки:**
1. `reality/auth.go` — x25519 + AuthID (AEAD)
2. `reality/handshake.go` — утилиты для Reality TLS (padding extensions)
3. `vless/header.go` — VLESS-заголовок
4. `vision/flow.go` — Vision flow

```go
// Упрощённая версия Reality handshake
func (r *RealityClient) Handshake() error {
    // 1. Генерация x25519 ключей
    myKey, err := x25519.GenerateKey(rand.Reader)
    
    // 2. ClientHello с Reality padding
    spec := r.buildClientHelloSpec(publicKey)
    if err := r.uconn.ApplyPreset(spec); err != nil { return err }
    if err := r.uconn.Handshake(); err != nil { return err }
    
    // 3. Вычисление AuthID
    authID := hkdf(publicKey, myKey, shortID)
    
    // 4. VLESS header (command=TCP, port, address)
    header := vless.EncodeHeader(userID, cmdTCP, port, address)
    if _, err := r.uconn.Write(header); err != nil { return err }
    
    // 5. Vision wrapping
    r.vision = vision.NewReadWriter(r.uconn)
    return nil
}
```

| Аспект | Оценка |
|---|---|
| **Implementation effort** | 🔴 Высокий (разработка и тестирование с нуля) |
| **Dependency weight** | 🟢 **Light** (только uTLS, x/crypto) |
| **Performance impact** | 🟢 None |
| **Long-term maintainability** | ✅ **Good** (собственный код, полный контроль) |

**Вердикт:** Идеально, но требует значительных трудозатрат. Если команда готова инвестировать ~2-4 недели — это лучший долгосрочный вариант.

### 6.4 Рекомендация по интеграции

**Phase 1 (MVP, 1-2 дня):** Использовать **Xray-core** как внешний прокси-процесс.  
Hasta-Vaquet client spawns `xray -c client.json` и перенаправляет трафик через SOCKS5 на `127.0.0.1:1080`. Это даёт немедленную поддержку Reality без изменения кода.

**Phase 2 (3-4 недели):** Реализовать **Custom Reality library** (Вариант D).  
Взять за основу sing-box или Xray-core код, но выделить его в отдельную библиотеку, используя только uTLS и `x/crypto`. Это даст минимальный бинарник, полный контроль и совместимость с текущей архитектурой.

**Phase 3 (необязательно):** Встроить **множественные транспорты** — клиент пытается Reality, падает на WSS, затем на UDP. Это максимально повышает отказоустойчивость.

```
Схема выбора транспорта в клиенте:

   Попытка Reality (TCP:443)
        |
        ├── успех → работаем
        |
        └── неудача (dial timeout / DPI block)
               |
            Попытка WSS (CDN:443)
               |
               ├── успех → работаем
               |
               └── неудача
                      |
                   Попытка QUIC-header UDP (19999)
                      |
                      └── успех → работаем
```

## 7. Заключение

### Лучшие Reality destinations

| Ранг | Домен | Почему |
|---|---|---|
| 🥇 | `www.microsoft.com` | Уже используется. Максимальная совместимость, низкий риск блокировки |
| 🥇 | `cdn.jsdelivr.net` | CDN-трафик — идеальная маскировка. Никакой корреляции с VPN |
| 🥇 | `www.bing.com` | Разрешён даже в Китае. Отличное правдоподобие |
| 🥈 | `www.apple.com` | iOS-экосистема даёт естественный «шум» |
| 🥈 | `www.cloudflare.com` | Дополнительная защита ECH |
| 🥉 | `www.wikipedia.org` | Образовательный трафик, низкий риск |

### Чего избегать

| Домен | Причина |
|---|---|
| `www.google.com` | Пост-квантовые эксперименты, стабильная блокировка в ряде стран |
| `www.youtube.com` | Целенаправленное замедление DPI (ТСПУ) |
| `api.github.com` | API-домен не маскируется под браузер |
| `discourse.example.com` | Невалидный домен (RFC 2606) |

### Рекомендованный план действий

1. **Оставить `www.microsoft.com`** как основной `dest` — работает стабильно
2. **Расширить `serverNames`** — добавить `cdn.jsdelivr.net`, `www.apple.com`, `www.bing.com`
3. **Интеграция Reality:** Phase 1 — Xray-core как внешний процесс; Phase 2 — собственная библиотека
4. **Рассмотреть мульти-inbound конфигурацию** для распределения клиентов по разным `dest`
5. **Мониторить блокировки** — если DPI начнёт детектить конкретный `dest`, переключиться на резервный
