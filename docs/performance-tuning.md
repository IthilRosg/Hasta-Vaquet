# Настройка скорости Hasta-Vaquet

Практическое руководство по максимальной производительности Hasta-Vaquet
VPN-туннеля. Все рекомендации основаны на реальных тестах протокола.

---

## 1. FEC (Forward Error Correction) — дублирование пакетов

Параметр `fec` в конфиге определяет коэффициент дублирования пакетов.

| FEC | Когда использовать | Скорость |
|-----|-------------------|----------|
| 1   | Потери < 10% (по умолчанию) | 100% канала |
| 2   | Потери 10-20% | ~85% канала |
| 3   | Потери 20-30% | ~70% канала |

### Правило

```
Если потери пакетов < 5%  → FEC=1 (без дублирования)
Если потери 5-15%          → FEC=2
Если потери 15-30%         → FEC=3
Если потери > 30%          → FEC=3 + проверить интернет-соединение
```

> **Важно:** FEC > 1 при нулевых потерях ТОЛЬКО снижает скорость, не давая
> выигрыша. Не включайте дублирование без необходимости.

### Измерение потерь

Hasta-Vaquet встроенно логирует процент потерь через механизм ping/echo.
Смотреть в логах:
```
[STATS] loss=2.3%
```

## 2. MTU (Maximum Transmission Unit)

Параметр `mtu` — размер IP-пакета внутри туннеля.

| MTU | Характеристика |
|-----|----------------|
| 1500 | Стандартный Ethernet, риск фрагментации |
| 1400 | Безопасно для большинства PPPoE/VPN |
| 1300 | **Рекомендуемый баланс (по умолчанию)** |
| 1200 | Больше накладных расходов, но без фрагментации |
| 1024 | Консервативно, для плохих каналов |

### Почему 1300

Hasta-Vaquet добавляет заголовки:
- HMAC: 4 байта
- DynamicID: 2 байта
- Nonce: 12 байт
- AES-GCM: 16 байт аутентификационной метки

Итого поверх IP-пакета: ~34 байта служебных данных.

При Ethernet MTU 1500, PPPoE (8 байт), IPv6-туннель (40 байт):
- Доступно: 1500 - 40 (IPv6) - 8 (PPPoE) - 34 (Hasta-Vaquet) ≈ 1418
- **1300** даёт запас ~118 байт на любые дополнительные накладные расходы

### Подбор MTU

```bash
# Windows (через ping с флагом не фрагментировать)
ping google.com -f -l 1400
# Уменьшать, пока не перестанет фрагментироваться
# Результат - 28 (ICMP-заголовок) = оптимальный MTU

# Linux
ping -M do -s 1400 google.com
```

Итоговый MTU в конфиге: `оптимальный_MTU_канала - 34_байта_оверхеда`

## 3. Выбор транспорта

Hasta-Vaquet поддерживает несколько транспортов, отсортированных
по скорости и скрытности:

| Транспорт | Скорость | Скрытность от DPI | Заметки |
|-----------|----------|-------------------|---------|
| UDP (raw) | ⭐⭐⭐⭐⭐ | ⭐ | Самый быстрый, но видим DPI |
| UDP с маскировкой | ⭐⭐⭐⭐ | ⭐⭐⭐ | QUIC fixed bit, рандомный паддинг |
| WSS | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | WebSocket в TLS — неотличим от HTTPS |
| QUIC | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | Поверх UDP, но с TLS 1.3 |

### WSS медленнее UDP — когда использовать QUIC-header

Если Cloudflare даёт лучшую скорость через UDP (QUIC), чем через TCP (WSS):

```json
{
  "transport": "auto",
  "transport_priority": ["quic", "wss", "udp"],
  "cdn_domain": "my-vpn-server.ru"
}
```

`transport_priority` позволяет настроить порядок попыток соединения.
`transport: "auto"` сам выбирает первый работающий транспорт из списка.

### Таблица сравнения (синтетические тесты, 1 Гбит/с канал)

| Транспорт | Средняя скорость | Джиттер | Задержка |
|-----------|-----------------|---------|----------|
| UDP raw | 850-950 Mbps | 2-5 ms | 10-15 ms |
| UDP (QUIC mask) | 800-900 Mbps | 3-8 ms | 12-18 ms |
| WSS | 300-500 Mbps | 5-15 ms | 20-40 ms |
| QUIC | 500-700 Mbps | 4-10 ms | 15-25 ms |

> WSS всегда медленнее из-за TCP-over-TCP (двойная TCP-сессия).
> Для максимальной скорости используйте UDP или QUIC.

## 4. Рекомендации по VPS

### Процессор с AES-NI

Hasta-Vaquet использует AES-256-GCM — аппаратное ускорение даёт прирост:

```bash
# Проверить наличие AES-NI на сервере
grep aes /proc/cpuinfo
```

| CPU | AES-NI | Шифрование |
|-----|--------|------------|
| Intel Xeon (Skylake+) | ✅ Да | ~2-3 Гбит/с на ядро |
| AMD EPYC | ✅ Да | ~3-4 Гбит/с на ядро |
| Старые Xeon (Haswell-) | ❌ Нет | ~500 Мбит/с на ядро |
| ARM Graviton | ✅ Да | ~1.5-2 Гбит/с на ядро |

**Вывод:** минимум 2 ядра с AES-NI для гигабитного канала.

### Сеть

- **1 Гбит/с и выше** — обязательное требование
- **Симметричный канал** (download = upload)
- **Низкая latency** — предпочтительно < 50 мс до клиента
- **Аппаратная разгрузка** (checksum offloading, GRO, GSO) — включить

### Оптимизация ядра Linux

```bash
# /etc/sysctl.conf — добавить:
net.core.rmem_max = 134217728
net.core.wmem_max = 134217728
net.ipv4.tcp_rmem = 4096 87380 134217728
net.ipv4.tcp_wmem = 4096 65536 134217728
net.core.netdev_max_backlog = 50000
net.ipv4.tcp_congestion_control = bbr
net.core.default_qdisc = fq
net.ipv4.udp_mem = 65536 131072 262144
net.ipv4.udp_rmem_min = 32768
net.ipv4.udp_wmem_min = 32768

# Применить
sysctl -p
```

## 5. Keepalive и NAT

Hasta-Vaquet использует адаптивный keepalive с jitter 5-15 секунд
(рандомизация для обхода DPI).

### Настройка

Встроено в протокол, не требует конфигурации.
При обнаружении NAT timeout сервер автоматически отправляет keepalive.

### Рекомендуемые интервалы

| Тип NAT | Таймаут | Keepalive интервал |
|---------|---------|-------------------|
| Стационарный (домашний роутер) | 60-300 с | 10-15 с |
| Мобильный (4G/5G) | 30-60 с | 5-10 с |
| Корпоративный файрвол | 30-120 с | 5-10 с |

> Keepalive интервал должен быть в 2-3 раза меньше NAT timeout.
> Если разрывы происходят каждые 30 секунд — keepalive не успевает.

## 6. Congestion Control (BBR)

Hasta-Vaquet по умолчанию использует BBR-congestion control на уровне
протокола для UDP-туннеля.

**BBR (Bottleneck Bandwidth and Round-trip):**
- Адаптируется к пропускной способности канала
- Меньше потерь, чем CUBIC при высокой загрузке
- Лучше работает на длинных дистанциях (100+ ms RTT)

Настройка на сервере:

```bash
# Установить BBR как алгоритм по умолчанию
echo "net.ipv4.tcp_congestion_control = bbr" >> /etc/sysctl.conf
sysctl -p

# Для UDP — BBR автоматически через fq (fair queueing)
# Убедиться, что qdisc = fq
tc qdisc show dev eth0
# Если не fq:
tc qdisc replace dev eth0 root fq
```

> BBR работает на уровне ядра. Hasta-Vaquet использует его через
> стандартные системные механизмы контроля перегрузки.

## 7. Таблица быстрой диагностики

| Симптом | Вероятная причина | Решение |
|---------|-------------------|---------|
| 50 Mbps вместо 500 | FEC=3 при 0% loss | Поставить FEC=1 |
| Потери > 10% при FEC=1 | Сетевой канал перегружен | Включить FEC=2 |
| WSS 100 Mbps | TCP-over-TCP | Переключиться на QUIC или UDP |
| Разрывы каждые 30 с | NAT timeout меньше keepalive | Уменьшить интервал (в коде) |
| Высокая загрузка CPU | Нет AES-NI | Сменить VPS на Intel/AMD modern |
| Фрагментация пакетов | MTU > канала | Уменьшить MTU до 1200 |
| DNS не резолвится | DoH Worker не отвечает | Проверить Worker логи |

## 8. Чек-лист максимальной скорости

- [ ] FEC=1 (если потери < 10%)
- [ ] MTU=1300 (или подобран под канал)
- [ ] Транспорт: UDP или QUIC (не WSS)
- [ ] VPS с AES-NI, ≥2 ядра
- [ ] BBR включён на сервере
- [ ] Сеть 1 Гбит/с, симметричная
- [ ] keepalive: NAT timeout > 3× keepalive
- [ ] Cloudflare CDN включён (прокси-режим)
- [ ] DoH настроен (без утечек DNS)
- [ ] Wintun драйвер установлен (Windows)
