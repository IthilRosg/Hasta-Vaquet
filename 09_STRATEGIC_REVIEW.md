## 2. Главная архитектурная проблема: дублирование кода

**В проекте ДВЕ реализации одного и того же протокола:**

- `main.go` (335 строк) — standalone клиент с СОБСТВЕННЫМИ `encrypt()`, `decrypt()`, `fnv1a16()`
- `core/crypto.go` (113 строк) — библиотечные `Encrypt()`, `Decrypt()`, `fnv1a16()`
- `core/vpn.go` (153 строки) — движок со `statsLoop`, `keepAliveLoop`, Echo-пингом
- `server/server.go` (461 строка) — ТРЕТЬЯ реализация `encrypt()`, `decrypt()`, `fnv1a16()`

**Три копии криптографии. Три независимых реализации одного wire format.**

Это значит:
- Любой багфикс в протоколе надо делать в 3 файлах
- Тесты криптографии не переиспользуются
- `main.go` НЕ ИМЕЕТ: statsLoop, RTT-замера, обработки echo `0x01`, нормальных колбеков
- `main.go` НЕ ИСПОЛЬЗУЕТ пакет `core/` вообще

**Это корневая причина большинства багов и застоя.**

## 4. Контекст РФ и мира (май 2026)

### Что происходит с VPN-блокировками:
- РКН активно блокирует VPN-протоколы на уровне DPI → наш кастомный протокол — **реальное преимущество**
- Банки (Сбер, ВТБ, Тинькофф) и Госуслуги определяют VPN через Android API (`IS_VPN`, `TRANSPORT_VPN`) → **Smart Bypass обязателен**
- Многие коммерческие VPN ушли из РФ или заблокированы → **ниша открыта**
- Пользователи массово переходят на самописные/нишевые решения → **спрос есть**
- Telegram временами троттлится, YouTube заблокирован → **VPN нужен ежедневно**

### Что это значит для проекта:
- **Протокол — наше главное преимущество.** HMAC-маркер + DynamicID + асимметричный паддинг + Bloom-фильтр — такого нет у конкурентов.
- **Но протокола мало.** Без kill switch и auto-reconnect пользователь сольёт реальный IP при обрыве. Без Smart Bypass пользователь не зайдёт в банк.
- **Android — приоритет #1.** Большинство пользователей в РФ на Android.
- **iOS можно отложить.** Дорого ($99/год), сложно (Apple review), маленькая доля рынка в РФ.

## 6. Корневые причины тупика

1. **Слишком много фаз = paralysis by analysis.** План на годы вперёд, а базовая функциональность не доделана.

2. **Три копии криптографии.** Любое изменение протокола — pain. Нет тестов. Нет уверенности.

3. **Нет реальных пользователей.** Протокол не тестировался против реального DPI РКН в полевых условиях. Всё в теории.

4. **Нет CI/CD.** Каждый билд — ручной. Каждый деплой — ручной.

5. **Android заброшен на 70%.** Статистика не интегрирована в UI. Kill switch не сделан. Без этого — не продукт.

6. **Нет фокуса на одной платформе.** Вместо того чтобы сделать Windows ИДЕАЛЬНО, распыляемся на Android, планируем macOS, iOS, Linux GUI...

## 7. Предлагаемый новый план: MVP First

### Фаза A: Consolidation (консолидация кодовой базы) — 1-2 дня

```
ЦЕЛЬ: ОДНА реализация протокола. ОДНА кодовая база.
```

- [ ] **A1. Удалить `main.go` standalone клиент.** Заменить на `cmd/client/main.go`, который использует `core/`.
  - Причина: `main.go` — мёртвый код, который только создаёт путаницу и баги.
  - GUI (`gui/`) уже использует `core/`. CLI должен делать то же самое.
- [ ] **A2. Выделить `server/encrypt/decrypt` в общий `core/` пакет.**
  - Сейчас в сервере третья копия. Надо чтобы сервер импортировал `core.Encrypt` / `core.Decrypt`.
  - Но `core/` зависит от `wintun` (Windows) и `golang.org/x/mobile` (Android). Это надо починить build tags.
- [ ] **A3. Вынести `fnv1a`, `bloomCheck`, `bloomSet` в `core/`.**
  - Сервер использует их — пусть импортирует.

### Фаза B: Kill Switch + Auto-Reconnect (Windows) — 1-2 дня

```
ЦЕЛЬ: Пользователь не теряет трафик при обрыве и не сливает IP.
```

- [ ] **B1. Kill Switch на Windows.** При падении UDP соединения или keep-alive таймауте > 60s — блокировать весь трафик.
  - Реализация: Windows Filtering Platform (WFP) через `netsh` или Win32 API — запретить весь трафик кроме UDP-порта сервера.
  - При восстановлении — убрать блокировку.
- [ ] **B2. Auto-Reconnect.** При обрыве — переподключение с экспоненциальным backoff (1s → 2s → 4s → ... → 60s cap).
  - UI показывает "Reconnecting..." с таймером.
  - Эта логика уже может быть добавлена в `core/vpn.go` как общая для Windows и Android.

### Фаза C: Добить Android — 2-3 дня

```
ЦЕЛЬ: Рабочий Android APK, который можно дать реальному пользователю.
```

- [ ] **C1. Интегрировать `GetStats()` в Android UI.** Сейчас статистика только через poll из Kotlin. Сделать отображение скорости, трафика, пинга.
- [ ] **C2. Kill Switch на Android.** VpnService.setAlwaysOn(true) + блокировка трафика без VPN.
- [ ] **C3. Auto-Reconnect на Android.** При падении — перезапуск VpnService.
- [ ] **C4. Smart Bypass: MVP.** Добавить `addDisallowedApplication` для Сбера + Госуслуг. Жёсткий список на первое время.

### Фаза D: Полевое тестирование — 1 неделя

```
ЦЕЛЬ: Подтвердить, что протокол реально обходит DPI РКН.
```

- [ ] **D1. Дать 5-10 реальным пользователям в РФ.**
- [ ] **D2. Собрать фидбек:** работает ли на их провайдере? Блокирует ли DPI? Работают ли банки с bypass?
- [ ] **D3. Итеративно фиксить проблемы.**
- [ ] **D4. Измерить реальную пропускную способность и стабильность.**

### Фаза E: Production — 1 неделя

```
ЦЕЛЬ: Продукт, готовый к платным пользователям.
```

- [ ] **E1. Срок жизни аккаунтов** (`expires_at` в конфиге).
- [ ] **E2. Квоты трафика** (`quota_bytes`).
- [ ] **E3. Windows installer** (Inno Setup).
- [ ] **E4. Приватная альфа для 50-100 пользователей.**

## 12. Резюме

**Проект не в тупике. Проект на правильном пути, но с неправильным фокусом.**

Сильные стороны:
- Свой крипто-протокол с реальной DPI-устойчивостью (это редкость)
- Работающий Windows GUI
- Работающий сервер с веб-панелью
- Архитектура готова к расширению (build tags, interface-based API)
- Deploy на реальном VPS с TLS (hasvaq.airydeck.su)

Слабые стороны:
- Три копии кода криптографии
- Нет kill switch — пользователь сливает IP
- Нет auto-reconnect — рвётся и всё
- Android не доделан (а это главная платформа для РФ)
- Нет реальных пользователей = нет обратной связи
- План на 15 фаз при готовности 3
- `math/rand` для паддинга — предсказуемо для DPI

**Что делать прямо сейчас:**
1. Консолидировать код (Фаза A) — 1-2 дня
2. Kill Switch + Auto-Reconnect (Фаза B) — 2-3 дня
3. Добить Android (Фаза C) — 2-3 дня
4. Найти 5-10 тестеров в РФ (Фаза D) — немедленно
5. Итерировать по фидбеку

**Через 2-3 недели можно иметь продукт, готовый к реальным пользователям.**

План на 15 фаз — положить в ящик. Вернуться к нему когда будет 100 платящих пользователей.
